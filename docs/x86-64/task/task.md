# 任务管理：程序是怎样“跑起来”的

这一章从“一个程序怎样变成正在运行的进程”讲起，逐步展开 osinfo 的任务、线程、调度、等待、退出与资源回收。读完之后，你应该能回答下面这些问题：

- 磁盘上的一个可执行文件，和内存里“正在运行的程序”差在哪里？
- 为什么要有“进程”和“线程”两个概念？它们各自保存什么？
- `fork` 到底复制了什么？为什么它通常和 `exec` 一起使用？
- 一个线程退出后，它的栈和页表为什么不能立刻释放？
- 调度器怎样决定下一个运行谁？上下文切换保存了哪些东西？

你不必先懂操作系统原理。文中第一次出现的术语都会解释；需要查代码时，直接看每节末尾给出的文件和函数名。

> 本章讲内核里的任务机制。用户态的 `task` 服务负责“读程序文件、启动程序、监督服务”，见[任务管理服务](../../service/task/task.md)。两边的分工在[第 10 节](#10-代码地图)说明。

## 0. 先记住三句话

1. **进程（Task）是资源容器**：它装着地址空间、句柄表、凭据、信号处理方式、父子关系等“这个程序拥有什么”。
2. **线程（Thread）是执行流**：它装着寄存器和栈，代表“CPU 正在替谁执行哪段代码”。一个进程至少有一个线程。
3. **调度器（Scheduler）决定谁上 CPU**：每个 CPU 有一条运行队列，调度器从中挑一个线程运行；被挑中的线程才真正占用 CPU。

把进程想成一家工厂，线程就是工厂里的工人：工厂提供厂房、机器、账本（资源），工人负责实际干活（执行指令）。工厂可以只有一个工人，也可以有很多工人共享同一个厂房。

## 1. 从磁盘上的文件到“正在运行的程序”

一个 ELF 可执行文件放在磁盘上时，只是一堆字节：代码段、数据段、符号表、入口地址。它既没有栈，也没有页表，更不会自己动起来。

要让它运行，操作系统至少要做四件事：

1. **建立地址空间**：为进程创建一张页表，把虚拟地址映射到物理内存。程序看到的地址是“虚拟”的，由 CPU 的 MMU 查页表翻译成真实内存地址。
2. **把代码和数据装进去**：按 ELF 的段信息映射文件内容，建立用户栈，把参数和环境变量放到栈上。
3. **准备执行现场**：设置好入口地址、栈指针、寄存器初值，让 CPU 第一次进入用户态时能从正确的位置开始执行。
4. **把它交给调度器**：创建一个线程对象，放进运行队列。之后调度器选中它，CPU 就开始执行这个程序。

这四件事分别对应本章的几个核心对象：`AddressSpace` 管第 1 步，ELF 加载管第 2 步，`Thread` 管第 3 步，`RunQueue` 和 `schedule()` 管第 4 步。

程序退出后，这些资源还要按相反顺序拆掉。**“怎么建”和“怎么拆”同样重要**，而且拆更难：可能有别的 CPU 还在用旧页表，可能有父进程还没取走退出状态，可能有设备还在通过 DMA 访问内存。后文会反复回到这个问题。

## 2. 三个核心对象

### 2.1 Task：进程控制块

`Task` 是内核里代表进程的对象，可以理解为“进程控制块（PCB）”。它保存的不是某一瞬间的寄存器，而是这个进程**拥有什么**：

| 成员/概念 | 作用 | 初学者容易误解的地方 |
| --- | --- | --- |
| `id_` | 进程号 PID | 线程也有编号；主线程的 TID 等于 PID |
| `addressSpace_` | 页表根、代数、地址空间锁 | 页表根是**物理地址**，不是虚拟地址 |
| `handles_` | 句柄表，进程打开的文件、端点等对象都从这里引用 | 句柄是进程内的编号，不是全局对象地址 |
| `threads_`、`mainThread_` | 线程链表和主线程 | 一个进程可以有多个线程 |
| `parent_`、`firstChild_` | 父子关系 | 父进程退出后子进程会被收养，不是立刻死亡 |
| `uid_`、`gid_`、`capabilities_` | 凭据和能力 | 权限检查看的是内核记录的身份，不是消息里自报的身份 |
| `signalActions_`、`pendingSignals_` | 信号处理方式和待处理信号 | 信号是“异步通知”，不是函数调用 |
| `state_`、`exitCode_` | 运行状态和退出信息 | `Terminated` 只表示逻辑上结束，资源可能还没释放 |

`Task` 自己有一把锁（`lock_`），保护状态、线程链、父子关系等字段。读这些字段时通常要持有这把锁，或者通过 `TaskReference` 延长对象寿命后再读。

### 2.2 Thread：执行流

`Thread` 保存“CPU 执行到哪了”：

- **内核栈**：线程在内核里执行系统调用、中断处理时用的栈。普通线程 64 KiB，固定角色的服务线程 256 KiB。
- **用户上下文**：用户态入口、用户栈指针、`RIP`、`RFLAGS` 等。发生系统调用或中断时，CPU 的现场会被保存到这里或内核栈上。
- **调度状态**：`Ready`、`Running`、`Blocked` 等，以及 `vruntime`、时间片、CPU 亲和性。
- **浮点状态**：512 字节的 FXSAVE64 区域。内核 C++ 只用通用寄存器，所以浮点状态属于用户线程，切换时要保存和恢复。
- **等待登记**：线程阻塞在哪个等待队列、哪个锁上，供唤醒和取消使用。

线程不是“进程里的一段代码”，而是**一次独立的执行**。同一个函数可以被多个线程同时执行，每个线程有自己的栈和寄存器。

### 2.3 AddressSpace：进程看到的内存地图

`AddressSpace` 保存三样关键东西：

- `rootPhysicalAddress_`：页表根的物理地址。切换进程时，内核把它写入 `CR3` 寄存器，CPU 之后就用这张页表翻译地址。
- `generation_`：地址空间代数。每次 `exec` 换掉页表根，代数加一。旧映射对象带着旧代数，清理时能发现“这已经是另一个地址空间了”，避免误删新映像的映射。
- `lock_`：保护页表根和映射操作。

`generation_` 从 1 开始，跳过 0。它解决的是一个很具体的问题：`exec` 前后虚拟地址可能完全相同，但背后已经是另一批物理页；如果只比较虚拟地址，旧对象的清理可能破坏新映像。

## 3. 状态：任务和线程的“人生阶段”

### 3.1 TaskState

| 状态 | 含义 | 注意 |
| --- | --- | --- |
| `Created` | 已分配对象，但还没有可运行线程 | 创建失败时由回收器直接丢弃，不产生僵尸 |
| `Running` | 至少有一个线程可以运行 | 不代表当前一定在 CPU 上 |
| `Terminated` | 逻辑上已结束 | 页表、句柄、线程栈可能还没释放 |
| `Stopped` | 被作业控制（如 SIGSTOP）暂停 | 这是 `state()` 返回的“视图”，内部仍可能是 Running |

`Task::state()` 会把“内部 Running + 被停止”呈现为 `Stopped`。这样做是为了让等待方和 `/proc` 看到一致的作业控制状态，而不必到处判断 `stopped_` 标志。

### 3.2 ThreadState

| 状态 | 含义 |
| --- | --- |
| `Created` | 对象已建立，但还没放进运行队列 |
| `Ready` | 可以运行，正在运行队列里等 CPU |
| `Running` | 当前正占用某个 CPU（或刚被选中） |
| `Blocked` | 在等某个条件（锁、IPC、子进程等），不能被调度 |
| `Sleeping` | 在等一个截止时间，挂在睡眠链表上 |
| `Stopped` | 被作业控制暂停 |
| `Terminated` | 已退出，但 CPU 可能还没离开它的栈 |

最后一行是关键：**`Terminated` 是逻辑状态，不是“资源已安全释放”的证明**。一个线程被标记为终止后，另一个 CPU 可能还在它的内核栈上执行最后几条指令。必须等上下文切换真正完成（后文的 `quiesceTask`），才能释放栈和页表。

## 4. 启动：kernel 任务和第一个用户进程

系统启动时还没有“进程”这个概念，但内核自己也要执行代码。osinfo 的做法是：

1. 引导线程（boot thread）已经在运行，`initThreads()` 为它建立一个 `Thread` 对象，直接复用当前的栈，不重新分配。
2. `init()` 建立一个特殊的 `kernel` 任务，把引导线程挂到它下面。这个任务负责给“没有所属进程的内核工作线程”一个归属。
3. 每个 CPU 的 `initScheduler()` 建立自己的运行队列和一个 idle 线程。没有普通线程可运行时，idle 执行 `sti; hlt`，让 CPU 睡眠，等中断把它叫醒，而不是空转浪费电。
4. 内核初始化完成后，通过 `startInitialProgram` 启动第一个用户态程序（`init` 服务）。它加载 ELF、建立用户线程，然后由调度器接管。

`kernel` 任务比较特殊：它没有用户地址空间，也不参与普通进程的 fork/exec。它的作用是给“没有所属进程的内核工作线程”（例如回收器线程）一个归属，并作为 init 不可用时的最终收养者。

## 5. 创建一个进程：fork 到底复制了什么

### 5.1 从用户代码到内核

用户调用 `fork()` 时，libc 最终发起系统调用，进入内核的 `TaskMechanisms::fork()`。内核不能直接相信用户传进来的指针，所以它先把“子进程的 fork 返回值 0”写进调用者的回复区，再开始创建子任务。

整体顺序可以概括为：

~~~mermaid
sequenceDiagram
    participant P as 父进程
    participant K as 内核 fork
    participant C as 子 Task
    P->>K: fork()
    K->>P: 在回复区写入“子进程返回 0”
    K->>C: Task::create()：新页表根、新 Task、空句柄表
    K->>C: 复制页表和映射（COW）
    K->>C: inheritForFork()：句柄、凭据、会话、限额、信号动作
    K->>C: 克隆用户态 MM 的 VMA/COW 状态
    K->>C: 创建可运行的子线程
    K-->>P: 父进程返回子 PID
    C-->>C: 子进程从 fork 返回 0
~~~

### 5.2 复制了哪些东西

`Task::create()` 做的是“从零建立一个进程”：

- 分配新的页表根（`mm::createAddressSpaceRoot()`）。
- 分配 `Task` 对象，初始化 64 槽的句柄表。
- 复制父进程的凭据（UID/GID、附加组）、资源限额、nice 初值、终端和会话信息。
- 把新任务挂到父进程的子进程链和全局任务表里。

`inheritForFork()` 做的是“把父进程的资源引用复制一份”：

- 遍历父进程句柄表，跳过带 `NoInherit` 标志的句柄。
- 端点（Endpoint）和共享内存要调用各自的 `duplicateHandle`，不能简单复制编号。
- 复制信号动作、命令行、认证会话等元数据。

**为什么不能直接复制句柄编号？** 因为句柄背后是内核对象和引用计数。复制编号而不增加对象引用，会导致父子进程共用一份引用，其中一个关闭时对象就被释放，另一个再用就是悬空引用。

### 5.3 写时复制（COW）

`fork` 如果真把父进程的每一页内存都复制一遍，会非常慢。osinfo 采用写时复制：父子进程先共享同一批物理页，页表项标记为只读；任何一方写入时触发缺页异常，内核再复制那一页，改成可写。

这样 `fork` 本身只需要复制页表和少量元数据，真正复制内存推迟到“有人要写”的时候。用户态 MM 服务负责克隆 VMA（虚拟内存区域）和 COW 状态，内核负责页表层面的映射。

### 5.4 失败与限制

- 拥有设备资源域的进程禁止 `fork`。设备可能正在通过 DMA 访问这块内存，复制地址空间会让“谁拥有这块设备内存”变得不明确。
- 任何一步失败，子任务的部分资源都交给回收器处理，而不是在调用者栈上随手释放。这样失败路径和正常退出路径共用同一套清理逻辑，减少遗漏。

## 6. 换一个程序：exec

### 6.1 为什么需要 exec

`fork` 复制出来的是父进程的副本，通常不是我们想运行的新程序。常见做法是：

1. `fork()` 创建子进程。
2. 子进程调用 `execve()`，把自己的地址空间替换成新程序的映像。
3. 父进程继续做自己的事，或者 `wait()` 等子进程结束。

`exec` 不是“再启动一个进程”，而是**同一个进程换掉自己的代码和数据**。PID 不变，但页表、地址空间内容、命令行等会替换；捕获型信号处理动作恢复默认，忽略型动作保留。

### 6.2 准备阶段与提交阶段

内核把 `exec` 拆成两段，原因是“准备可能失败，而提交不能失败”：

- **准备阶段**（`TaskMechanisms::replace`）：读取新 ELF、共享库、参数、环境变量，建立新的页表根和用户栈。这一步可能因为文件不存在、格式错误、内存不足而失败。失败时旧映像必须完好无损。
- **提交阶段**（`Task::commitExec`）：一旦开始，就不能回头。要终止其他线程、等待远端 CPU 停稳、释放旧映射、切换页表根、关闭 `CloseOnExec` 句柄、销毁旧页表根。

### 6.3 commitExec 的关键步骤

`commitExec` 运行在调用线程上，持有一把“不可抢占”的保护，但**保持中断开启**，因为要通知其他 CPU 重新调度。它大致做这些事：

1. 拒绝 kernel 任务、已终止任务和不属于当前线程的调用。
2. 在 Task 锁内终止除当前线程外的所有线程，把它们从线程链摘下，标记退出已记账。
3. 清空当前线程的信号帧、等待链、临时引用等“属于旧映像”的状态。
4. 把当前线程设为主线程，线程计数改为 1，关闭“接受新线程”开关。
5. 释放 Task 锁，调用 `quiesceTask()` 等待其他 CPU 离开这个任务。
6. 通知设备资源域“所有者正在退出”，取消旧端点、旧等待，执行 `ThreadCleanup`。
7. 释放旧映射登记，切换地址空间根（写 `CR3`），关闭 `CloseOnExec` 句柄，销毁旧页表根。
8. 重新允许新线程，返回成功。

**为什么第 5 步不能持锁？** 因为其他 CPU 可能正需要这把锁才能完成切换；持锁等待会死锁。**为什么不能在第 2 步之后失败？** 因为兄弟线程已经被终止，旧地址空间已经半拆，没有“恢复原状”的可靠路径。所以所有可能失败的准备工作都必须放在提交之前。

### 6.4 提交成功后怎样返回

`exec` 成功后不应该返回到旧程序的调用点，而应该从新程序的入口开始执行。内核把当前系统调用的上下文标记为“已恢复”（`contextRestored`），返回路径直接进入新映像，不再往旧回复区写数据。

## 7. 等待、退出与回收

### 7.1 退出不是“删掉”

一个进程退出时，内核不能立刻把 `Task` 对象删掉，原因至少有四个：

1. 父进程可能还要 `wait()` 取退出状态（这就是“僵尸进程”存在的原因）。
2. 其他 CPU 可能还在执行这个任务的线程。
3. 设备可能还在通过 DMA 访问这个任务的内存。
4. core dump 可能还在写，退出状态里的“是否已转储”标志还没最终确定。

所以 osinfo 把退出拆成“逻辑终止”和“物理回收”两个阶段。

### 7.2 退出路径

`exitCurrent(code)` 处理整个进程退出：

1. `terminateOtherThreads(code)`：关闭新线程接纳，终止除当前线程外的所有线程。
2. `exitCurrentThread(code)`：结束当前线程。
3. 线程退出时取消 IPC、执行临时引用清理、登记退出。
4. 最后一个线程退出时，把 Task 标记为 `Terminated`，提交给回收器。
5. 回收器异步释放资源，并在合适的时机通知父进程。

`exitCurrentThread` 是 `[[noreturn]]` 的：它把线程标记为终止，调用 `schedule()` 切到别的线程，**不会返回到自己的栈上**。因此它不能在自己的栈上释放当前内核栈，只能交给后续的上下文切换或回收器。

### 7.3 退出状态编码

`wait` 取到的状态沿用 POSIX 的编码习惯：

- 正常退出：`(exitCode & 255) << 8`。
- 信号退出：低 7 位是信号号；如果 core 已写出（Complete 或 Truncated），再置 `0x80`。
- 停止：`(signal << 8) | 0x7f`。
- 继续：`0xffff`。

core 还在处理时，父进程的最终退出结果会被延迟报告，避免父进程先看到“没有 core”，而实际上 core 随后写成功了。

### 7.4 僵尸与孤儿

- **僵尸进程（zombie）**：已经退出，但父进程还没 `wait()`。它的 `Task` 对象、退出状态和统计信息还保留着，但地址空间、线程、句柄已经释放。僵尸不是 bug，是“退出状态还没被取走”的正常中间状态。
- **孤儿进程（orphan）**：父进程先退出，子进程还活着。内核会把子进程转交给 `init`；如果 `init` 不可用，就转交给 `kernel` 任务。转交发生在回收器里，通过 `adoptChildren()` 完成。

### 7.5 回收器（TaskReclaimer）

`TaskReclaimer` 是一个没有所属进程的内核工作线程。它从队列里取出待回收的 `Task`，调用 `Task::destroyResources()`。为什么需要独立线程？因为申请销毁别人任务的线程可能自己先退出；把清理责任交给一个独立、持久的线程，才能保证资源最终被释放。

`resourceState_` 有三个值：

| 值 | 含义 |
| --- | --- |
| 0 | 未提交回收 |
| 1 | 已提交，等待回收器处理 |
| 2 | 已回收完成 |

`destroyResources()` 的顺序很重要：

1. 关闭线程接纳，终止剩余线程，把线程计数清零。
2. 释放 Task 锁，调用 `quiesceTask()` 等待远端 CPU 停稳。
3. 通知设备资源域“所有者退出”，停止可能还在进行的 DMA。
4. 在旧页表根还存在时采集 core 快照。
5. 把地址空间根置零，撤销端点所有权。
6. 取消所有线程的等待，执行 `ThreadCleanup`，释放线程栈。
7. 收养子进程，释放句柄表、普通映射、共享映射和旧页表。
8. 通知设备“地址空间已释放”。
9. 对从未启动过线程的 `Created` 任务，直接从父子链和全局表摘除；正常退出的任务保留到父进程 `wait()`。

### 7.6 wait 的返回值

`Task::waitForChild` 不直接睡眠，它只检查状态并登记等待，真正阻塞由 task.kernel 的请求循环完成。返回值约定：

| 返回值 | 含义 |
| --- | --- |
| `0` | 已经拿到结果（或事件） |
| `1` | 已登记等待，需要阻塞后重试 |
| `2` | 非阻塞（NOHANG）且暂时没有事件 |
| `-1` | 没有符合条件的子进程，或参数不合法 |

`waitid` 的 `WNOWAIT`（不消费事件）通过 `peek` 实现：报告事件，但不摘链、不清除停止/继续标志，方便后续的消费型等待再取一次。

## 8. 调度：下一个是谁

### 8.1 每个 CPU 一条运行队列

osinfo 的调度器是 per-CPU 的：每个 CPU 有自己的 `RunQueue`，里面有一棵按虚拟运行时间排序的红黑树。线程在同一时刻只属于一个 CPU 的运行队列；跨 CPU 迁移时要持有目标队列的锁。

红黑树是一种自平衡二叉搜索树，插入、删除、找最小值的复杂度都是 O(log n)。调度器每次都取“最左边”的节点，也就是 `vruntime` 最小的线程。

### 8.2 CFS 与 nice

调度器采用 CFS（完全公平调度器）风格：

- 每个线程有一个 `vruntime`，表示“已经享受过多少 CPU 时间”，但按权重折算。
- nice 值范围 -20 到 19，越小优先级越高。nice 0 的权重是 1024，-20 约 88761，19 只有 15。
- 每次运行后，`vruntime` 增加：

```text
deltaVruntime = (实际运行纳秒数 * 1024 + 权重 - 1) / 权重
```

权重越大，同样的实际运行时间只增加很少的虚拟时间，于是更容易再次被选中。这样既保证“按权重分配 CPU”，又不需要复杂的固定优先级队列。

默认时间片是 4 ms。注意：**这不是实时调度保证**，只是让线程在被抢占前至少跑一小段，减少切换开销。

### 8.3 schedule() 做了什么

`schedule()` 的流程可以简化为：

1. 关中断，取当前 CPU 的运行队列，加锁。
2. 如果当前线程仍然是 `Running`，把它重新插回红黑树（它刚才被摘出来运行）。
3. 取红黑树最左节点；如果没有，就选 idle 线程。
4. 把选中的线程从树上摘下，设为 `Running`，重置时间片，更新当前线程和当前 Task。
5. 释放队列锁。
6. 如果换了线程：设置目标内核栈、切换页表根（写 `CR3`），调用 `Thread::switchTo(next)`。
7. 切换完成后，`finishContextSwitch()` 处理旧栈的退役和 `executingTasks` 的发布。

**为什么第 5 步要先释放锁再切换？** 因为切换后执行的是另一个线程的代码，它不应该“继承”上一把锁的持有状态。锁的所有权属于线程，不属于 CPU。

### 8.4 上下文切换保存什么

`switchThreadContext` 是汇编实现的，它做三件事：

1. 把 `RFLAGS` 和 15 个通用寄存器压到当前线程的内核栈。
2. 把当前 `RSP` 保存到 `previous->stackPointer`。
3. 把 `next->stackPointer` 装入 `RSP`，按相反顺序弹出寄存器和标志，`ret` 到目标线程的下一条指令。

浮点状态单独用 `fxsave64` / `fxrstor64` 保存和恢复。内核 C++ 不使用浮点寄存器，所以用户线程在系统调用里被切换时，浮点状态仍然属于它。

### 8.5 阻塞与唤醒：wakePending 窗口

线程阻塞的典型顺序是：

1. 持有保护条件的锁，检查条件。
2. 调用 `prepareCurrentWait()` 清除旧的唤醒标记。
3. 把线程挂到等待队列。
4. 释放条件锁。
5. 调用 `blockCurrentThread()` 真正睡眠。

问题在于：第 3 步和第 5 步之间，另一个 CPU 可能已经调用了 `wakeThread()`。如果唤醒方看到线程还是 `Running`，只是设一个 `wakePending` 标志；等线程执行到 `blockCurrentThread()` 时，先检查这个标志，发现已经被唤醒，就不进入 `Blocked`，直接返回。这样就不会丢唤醒。

### 8.6 睡眠、时钟与抢占

- `sleepCurrentThread(ms)` 把线程挂到按截止时间排序的睡眠链表，然后调度走。`schedulerTick()` 每秒 1000 次检查到期线程，把它们移回运行队列。
- `requestReschedule()` 只设置“需要重新调度”的标志，真正的切换发生在中断返回或显式调用 `schedule()` 时。
- 一个 CPU 要终止另一个 CPU 上的线程，不能直接改它的栈；只能标记终止并发送“重新调度”请求，让对方自己切走。
- `quiesceTask()` 同时检查“目标 CPU 已选中的线程”和“已完成切换的 `executingTasks`”，覆盖 `switchTo` 前后两个窗口，确保没有 CPU 还在目标任务的栈上。

## 9. 并发与生命周期：为什么释放这么麻烦

任务管理里最难的从来不是“创建”，而是“什么时候可以安全释放”。下面几条规则贯穿整个模块：

### 9.1 锁的层次

| 锁 | 保护什么 | 典型使用者 |
| --- | --- | --- |
| 全局任务表锁 `taskListLock` | 全局任务链表、按 PID 查找 | `find`、`at`、`next`、`unlinkGlobal` |
| `Task::lock_` | 进程状态、线程链、父子链、信号动作 | 创建、退出、wait、凭据修改 |
| `AddressSpace::lock_` | 页表根和代数 | `replaceRoot`、映射操作 |
| `RunQueue::lock` | 就绪树、睡眠链、当前线程 | 入队、出队、唤醒、时钟 |

这些锁不能互相替代。例如：调度队列锁保护“线程在不在树上”，但不保护“页表根指向哪里”；地址空间锁保护页表根，但不保护“线程是否还在 CPU 上”。

### 9.2 引用计数与 TaskReference

裸 `Task*` 指针只在持锁的短临界区内安全。一旦要释放锁、可能阻塞、或者跨函数返回，就必须用 `TaskReference`：

- 构造时增加 `Task` 的引用计数，并把释放动作登记到当前线程的 `ThreadCleanup` 链。
- 即使线程被强制终止、没有执行 C++ 栈展开，`ThreadCleanup` 也会在退出路径上释放引用。
- 引用计数只保证 `Task` 对象还活着，**不保证它的旧地址空间还能访问**。`exec` 或回收之后，对象可能还在，但页表已经换掉或销毁。

访问句柄背后的对象时，用 `HandleTable::Pin` 固定引用；不要把句柄编号当指针长期保存。

### 9.3 三个“不等于”

- `Terminated` ≠ CPU 已离开：还要等 `quiesceTask`。
- 对象还有引用 ≠ 旧页表有效：`exec` 会换根，回收会销毁根。
- 线程切走 ≠ DMA 已停止：设备可能还在访问内存，必须等设备资源域确认。

### 9.4 推荐的释放顺序

1. 先关闭“接受新工作”的入口（新线程、新请求）。
2. 标记所有执行者终止，并请求远端 CPU 重新调度。
3. 等远端 CPU 停稳（`quiesceTask`）。
4. 停止设备访问，采集 core。
5. 取消等待、执行清理登记、释放栈。
6. 释放句柄、映射、页表根。
7. 最后才释放 `Task` 对象本身。

这个顺序在 `commitExec` 和 `destroyResources` 中都能看到。改动其中任何一步，都要重新检查“谁还可能在使用被释放的资源”。

### 10.1 内核 task.kernel 与用户态 task 服务

两者名字相近，职责不同：

- **内核 `task.kernel`**（`src/kernel/task/service/`）：提供“建立/切换执行上下文、检查权限、等待状态、资源回收”等机制。它不读磁盘上的程序文件，也不决定该启动哪个服务。
- **用户态 `task` 服务**（`src/task/main.cc`）：负责读取 ELF、解析参数、创建子进程、监护 pipe/msgq 等子服务。它通过 IPC 请求内核机制完成真正危险的操作。

这种划分遵循“机制与策略分离”：内核只提供最小、可信、不可绕过的机制；启动什么程序、怎样监督，放在用户态服务里，便于修改和替换。

## 11. 常见误解

**问：一个进程只有一个线程吗？**
答：不一定。进程是资源容器，可以包含多个线程。主线程的 TID 等于 PID，其他线程有独立 TID。

**问：线程退出后，它的栈马上就释放了吗？**
答：没有。线程被标记 `Terminated` 后，CPU 可能还在它的内核栈上执行。必须等上下文切换完成，或者由回收器在确认安全后释放。

**问：`fork` 会复制父进程的全部内存吗？**
答：逻辑上是“复制”，物理上通常用写时复制。父子进程先共享物理页，写入时才真正复制。

**问：`exec` 会创建新进程吗？**
答：不会。`exec` 替换当前进程的地址空间和映像，PID 不变。

**问：僵尸进程是内存泄漏吗？**
答：不是。僵尸只保留 `Task` 对象和退出状态，地址空间、线程、句柄已经释放。父进程 `wait()` 取走状态后，对象才会被回收。

**问：`Terminated` 表示资源已经释放了吗？**
答：不表示。它只表示逻辑上结束。资源释放要经过回收器，并且要等远端 CPU 停稳、设备停止访问。

**问：调度器会保证高优先级线程立刻运行吗？**
答：不会。nice 只影响 CPU 时间分配比例，不是实时保证。线程被唤醒后只是变为 `Ready`，什么时候上 CPU 仍由运行队列决定。

## 12. 术语表

| 术语 | 解释 |
| --- | --- |
| 进程（Task） | 资源容器：地址空间、句柄、凭据、信号动作、父子关系等 |
| 线程（Thread） | 执行流：寄存器、栈、调度状态；一个进程可以有多个线程 |
| 地址空间（AddressSpace） | 虚拟地址到物理地址的映射，核心是页表根 |
| 页表根 / CR3 | 页表最顶层的物理地址；写入 CR3 即切换地址空间 |
| 句柄（Handle） | 进程内用来引用内核对象的编号，需配合句柄表使用 |
| 端点（Endpoint） | 进程间通信的端口，消息通过它排队和传递 |
| 上下文切换 | 保存当前线程的寄存器/栈，恢复另一个线程的执行现场 |
| 运行队列（RunQueue） | 每个 CPU 上等待运行的线程集合，按 `vruntime` 排序 |
| 虚拟运行时间（vruntime） | CFS 用来衡量“已经享受过多少 CPU 时间”的折算值 |
| 时间片（Time slice） | 线程一次连续运行的时间上限，默认 4 ms |
| 阻塞（Blocked） | 线程在等条件，不能被调度，直到被唤醒 |
| 停稳（Quiesce） | 确认所有 CPU 都不再执行某个任务的代码 |
| 回收（Reclaim） | 释放已终止任务的线程栈、句柄、映射和页表 |
| 僵尸进程（Zombie） | 已退出但父进程尚未 `wait()` 的进程 |
| 孤儿进程（Orphan） | 父进程先退出、仍存活的子进程，会被 init 收养 |
| 写时复制（COW） | 父子进程先共享物理页，写入时才复制 |
| core dump | 进程异常终止时把内存快照写到文件，便于事后调试 |
