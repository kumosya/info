# pipe 服务

src/task/pipe/main.cc 的 PipeServer 在 Ring3 保存管道和双向通道的字节缓冲区、EOF、非阻塞标志及待回复请求。内核中没有 PipeState 或管道后端。

每条流容量 16 KiB，单次协议数据最多 512 字节，最多 64 对端点、128 个延迟请求。句柄是不可伪造的 Endpoint 能力标签：服务按内核对象 ID 查找状态，按传递的 rights 校验读写权限；客户端不能通过猜测整数 ID 获得访问权。

阻塞操作保存 Reply Token，不阻塞服务主线程。服务查询 Token 是否仍有效，取消/超时后释放所持能力引用。最后一个写方关闭产生持久 EOF；通道 EOF 是一次性事件。对象引用消失后销毁标签并回收 Ring3 缓冲状态。

使用现有 IPC、句柄子操作和恢复域，不增加 syscall。完整检查点保留流、能力标签、游标、EOF 和非阻塞状态；增量事务提交后才回复成功。重启先恢复同一业务对象，再发布 ready。

## 引导与权限

task 由 init 创建后，首先创建并监护 pipe，等待注册名 pipe 就绪，再创建 msgq。pipe 为独立 Ring3 镜像，角色 Pipe，不依赖 PCI；控制经 control.task 路由，父任务句柄不由 init 重复持有。

PipeOperation 在 os/core_service.h 定义。Create/CreateChannel 返回两个能力句柄；Read/Write 带一个端点标签，data[1] 为最多 512 字节的长度，写数据从 data[3] 开始；Read 回复状态/字节数与数据。Identity/Nonblocking/Eof 只接受已有标签及所需 rights；非法句柄、权限、满缓冲、对端关闭分别返回错误。

主线程串行推进 Pair 与 Pending，等待通过 Reply Token 保存，不阻塞处理其他管道。pending 持有引用，客户端取消/死亡后查询 token 并释放；双方引用消失才释放 Pair。通道 EOF 与最后写引用关闭分开，PTY 不能用永久泄漏的客户端副本维持假存活。

基础 pipe 拒绝永久停止/禁用；受控 restart 经 control.task 执行，普通 kill 保护不变。服务重启不关闭客户端原有的管道/通道标签，也不创建替代流冒充旧对象。

## 提交、请求去重与恢复

每次变更先预留日志空间，随后修改字节/游标、保存请求结果、提交不可变记录，最后回复。记录只含对象元数据、消费游标和本次最多 512 字节的写入，不逐次复制整份 64 对流缓冲。日志达到配额时先生成完整检查点；空间分配失败在业务修改前返回错误。恢复版本与校验和不匹配则拒绝 ready。

SDK 给请求附稳定 ID，结果键包含内核认证的 PID/TID 与地址空间代次，摘要校验原操作、数据和传入能力身份/权限。服务退出导致 IPC 失败时，客户端在 20 秒内以原 ID 续接；已提交读直接返回原字节，不次消费。客户端信号中断或超时只查询已提交结果，没有提交时返回原中断/超时，不把取消的读取重新排队。

回复到达客户端后发送精确请求 ID 与原 TID 确认，结果与返回能力随确认退休。确认暂时失败时放入 SDK 的有界待确认表，后续调用每次最多补发四项；同一进程其他线程也可确认，但必须匹配原 PID/TID 与地址空间代次。不能用“同线程出现更大 ID”代替确认：信号处理器可能嵌套写入，此时外层读取的已提交结果仍需保留。结果表最多 128 项，满时拒绝新变更，不能覆盖未确认的消费结果。退出/exec 的旧结果按 Task 代次回收；恢复时丢弃无副作用的未完成结果，让原客户端重新发起。reply token 与 pending 本地句柄不进入日志。

恢复引用不计为业务端引用。未确认 Create 结果临时保留流，防止尚未交付的能力被收走；确认之后，最后一个写端关闭仍产生 EOF，双方都关闭才销毁流。共享标签恢复时校验对象 ID、权限及唯一性，不能靠旧局部句柄号重新猜对象。

`tests/pipe-recovery.sh` 使用专用测试内核和服务，在读/写修改后提交前、提交后回复前四个位置强退服务，检查旧字节、消费去重、半关闭、非阻塞、能力身份和阻塞客户端重连；还验证信号中断与已提交消费的交错。故障钩子仅存在于测试构建，不是运行时配置。
