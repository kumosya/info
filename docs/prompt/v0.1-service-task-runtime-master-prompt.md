# OSInfo 0.1 系列：服务启动、任务接口、进程工具与桌面稳定性总执行 Prompt

你正在维护 OSInfo 0.1 系列。按本文件完成服务启动与监护重构、运行时配置、systemctl、任务 API 统一、虚拟目录、进程查看与信号工具、终端会话恢复、GUI 连续点击崩溃修复，以及详细服务文档。

本文件汇总本轮已经确认的需求。早期 Prompt 和进度文档只作为历史背景；与本文件冲突的旧启动顺序、路径、API、工具归属及验收结论不能继续沿用。先核对当前源码，再实施；不能把历史测试通过当作本次改动的验证证据。

## 1. 工作范围与硬约束

### 1.1 项目边界

- OS：`D:/osinfo/info`。
- 基础工具：`D:/osinfo/osinfo-base-tools`。
- GUI：`D:/osinfo/guiw`，包括窗口服务与终端应用。
- 包管理：`D:/osinfo/inpkg`。
- 开发工具：`D:/osinfo/infoide`。
- 清点 `D:/osinfo/` 下实际使用 SDK 的其他项目，仅在接口、标准头或生成模板适配确有需要时修改，不扩展无关产品功能。
- Windows 路径表示工作区位置。构建和运行使用 Linux 路径，不在生产代码中写死 WSL 发行版、盘符或相邻仓库路径。

### 1.2 必须保持的边界

- **不修改、移动、改名或删除任何架构规格文件，包括 `docs/architecture.md`。** 可以阅读和引用；实现与旧架构描述有差异时，在本轮进度记录中说明。
- Ring3 服务位于 `src/`，Ring0 服务与机制位于 `src/kernel/`；`user/` 用于应用，不用于放置服务。
- pci/storage 属于 device 子树，pipe/msgq 属于 task 子树。独立服务分别构建，不能递归把子服务 main 链入父服务。
- 复用已有 syscall 与 IPC。禁止在 `.kernel` 服务中重新实现已有的映射、取消映射和保护等 syscall 业务，也不能增加任意硬件 I/O 代理。
- 不新增 Python 文件。C++ 与 Shell 完成构建辅助、配置处理和测试；测试放 `tests/`，不放生产 `script/`，不新增独立的冒烟测试配置文件。
- 只有 `packages/` 包目录。应用与 OS 源码隔离，OS 消费发布包，不在构建过程中执行相邻应用项目的构建命令。
- OS 的 `make run/debug` 保持硬盘启动，通过 `make install` 更新已有系统镜像；默认不重装 GRUB，不恢复 `cpfiles`。
- InfoIDE 的安装、卸载、发行包生成继续完全归 InfoIDE 项目。OS 只提供通用 IMG/ISO 和公共 SDK，不重新引入 InfoIDE 专用安装目标。
- InfoIDE 默认项目硬盘调试；只有显式选择才使用光盘。保留现有安装布局、卸载功能和项目根目录内镜像约束。
- 不主动创建分支、提交、推送、重置或清理用户既有改动。读取并遵守适用的 AGENTS.md；确需确认的高风险操作先准备准确范围，再按现有授权与确认规则处理，不反复请求已经获得的授权。
- 遵循 KISS、DRY、YAGNI、SOLID。保留现有注释语言，不加入本轮不需要的框架、热重载、远程控制或兼容别名。

## 2. 执行前核对与基线

以下是制定本 Prompt 时观察到的事实，修改前必须再次核对：

1. `tools/host/generate.cc` 生成 `startup.inc`、`sessions.inc`，init 将它们包含进 C++ 程序。
2. 配置标记为 `local/disk/external` 的 Ring3 服务目前都生成 GRUB 模块，并统一通过固定 ProgramId 启动；不能只把 C++ 数组改成文本就宣布文件加载已完成。
3. init 直接启动 pci、pipe、msgq 等全部服务；现有依赖中 task 等待 pipe/msgq，pipe/msgq 又依赖 pci，需要按新的父子关系重排。
4. 普通文件 SpawnImage 禁止非零 serviceRole/capabilities，不能直接用普通 execute 替代特权服务启动而跳过授权设计。
5. 公共任务接口是 `os::Process`，`TaskListEntry/listTask` 被 ps、pkill、killall 使用；当前列表来自 task 服务维护的记录，不保证覆盖全系统进程。
6. `/sys` 有节点描述和内容读取实现，但用户报告 `ls /sys` 无法正常列出内部内容；必须从实际目录调用链定位问题，不能假定只是 ls 显示错误。
7. init 启动文本 shell 后缺少完整的逐 TTY 会话监护；GUI 终端的 shell、PTY、读线程和标签页也需要核查退出处理。
8. 用户仍可复现鼠标连续点击导致图形界面崩溃。历史“100 次点击通过”不足以说明问题解决。
9. 此前另记录过一次内核在服务启动前报告 `probe thread affinity failed`。该现象与点击崩溃分开取证，不能未经分析归为同一个问题，也不能通过无限重试掩盖。

先记录仓库状态、构建入口、关键接口使用方、SDK/包版本以及当前可复现操作。保存崩溃前后的串口日志和有关资源状态；避免在完成故障基线前大范围修改导致原问题失去复现条件。

## 3. C++ 标准头统一

### 3.1 目标与范围

- 项目中的 `.cc/.cpp/.cxx` 及 C++ 专用头文件使用 C++ 标准包装头。

- 清点 OS、基础工具、GUI、inpkg、InfoIDE、测试、代码生成模板和 SDK 源输入，不只替换 OS 的 src 目录。
- 不是给文件名机械增加 c 前缀；按标准对应关系转换。

对应关系包括但不限于：

### 3.2 边界与验证

- `<unistd.h>`、`<fcntl.h>`、`<sys/stat.h>` 等 POSIX 头没有相应标准 C++ 包装头，不机械改名。
- 不把同名项目私有头、带引号的项目包含或第三方 C 实现误改为标准头。
- C/C++ 共用头必要时使用条件包含，不能让 C 编译器解析 cstdint 等 C++ 头。
- 补齐自有标准库缺失的包装头和命名空间适配，避免仅靠宿主系统头让 freestanding 构建假通过。
- 标准名迁移与实现相关名称空间改动按实际声明核对，不做不区分语义的全局替换。
- 重新导出 SDK、更新包内头文件并重建调用方；扫描结果与构建结果共同验收。

## 4. `os::Process` 改为 `os::Task`

### 4.1 公共 API

将 OS 公共类 `os::Process` 全面改为 `os::Task`，不保留旧类别名。方法内重复的 Task 名称移除，主要对应关系：

| 原名 | 新名 |
| --- | --- |
| getTaskId | getId |
| getTaskState | getState |
| getTaskInfo | getInfo |
| queryTask | query |
| terminateTask | terminate |
| waitTask | wait |
| killTask | kill |
| getTaskIdentifiers | getIdentifiers |
| setTaskGroup | setGroup |

其他方法按同一规则逐项核对，保留必要的 Thread、Session、Signal 等语义。清楚区分 PID、TID 和 TaskHandle；`getInfo(handle)` 与 `query(pid)` 不能因改名而混用。

### 4.2 删除旧列表接口

- 删除公共 `listTask` 函数与 `TaskListEntry` 结构体。
- ps/pkill/killall 的枚举统一改用 `/proc`。
- 不另设公共 enumerate/list 别名绕开这项要求。FS 构造 procfs 必需的内核枚举可以作为内部查询机制，不要求 FS 反过来读取自己提供的 `/proc`。
- 清理只为旧列表服务的无用协议、包装和跟踪逻辑；先核对进程监护、句柄持有、Wait/Kill 是否仍依赖其中部分状态，不误删仍有职责的记录。

### 4.3 ABI 与调用方

- 同步声明、定义、显式符号字符串、可信导入解析、内联包装、libc 适配、测试和文档。
- libc 的 POSIX C 接口名称不随 C++ 类改名而更改。
- InfoIDE 自己启动宿主进程的辅助类不是 `os::Process`，不能盲目替换。
- 重新构建运行库、服务、基础工具、GUI、inpkg；更新 SDK 与所有受影响发布包，禁止混用旧 ABI 二进制。

## 5. `/sys` 和 `/proc` 的目录与信息实现

### 5.1 先修复虚拟目录基础语义

沿实际 VFS 与应用调用链检查目录打开、路径分发、readdir、stat/lstat、目录句柄和结束返回值。

- `ls /sys` 应列出实际存在的子目录与文件。
- 覆盖 `/sys/kernel`、`/sys/cpu`、`/sys/memory` 等嵌套目录以及尾部斜杠。
- 虚拟目录不能错误落入磁盘文件系统枚举。
- 目录大小为零不代表目录为空；目录结束与读取错误分别处理。
- 列出条目的名称、类型、inode、权限与后续 stat/open 一致。
- 正确处理未知 d_type、偏移推进和点目录约定，避免遗漏、重复或无限循环。
- 修正 FS 或 ls 中实际存在的问题，不用给 ls 硬编码 `/sys`、`/proc` 特例掩盖 VFS 缺陷。

### 5.2 procfs 进程节点

至少提供：

```text
/proc/self
/proc/<pid>/stat
/proc/<pid>/status
/proc/<pid>/cmdline
/proc/<pid>/comm
```

元数据来自内核实际进程状态，而不是 task 服务仅记录的程序列表。包括：

- PID、PPID、UID/GID、有效 UID/GID、状态。
- 进程组、会话 ID、控制终端和前台进程组。
- 启动时刻与累计 CPU 时间，以及它们的单位、时间基准。
- 程序名、启动参数；cmdline 的 NUL 分隔格式与可见权限。
- 服务标记、所属管理者等诊断字段。

要求：

- 明确定义文件格式、读取权限、内核内部任务的呈现规则及退出/僵尸状态。
- 控制终端是会话元数据，不能用 stdin 路径替代；正确维护 fork/exec/setsid/终端获取释放后的值。
- `/proc/self` 按发起请求的调用方解析，不得错误指向 FS 服务自身。
- 同一次打开的分段读取保持内容和偏移一致，不能因实时内容变化拼接出损坏记录。
- 枚举期间进程新建、退出属于正常竞争；不能提前终止整个目录、重复条目、泄漏对象或返回失效引用。
- 对多线程进程的时间与状态按定义汇总，不把每个内部线程误当独立用户进程。
- cmdline 和终端输出防止无边界字符串、越界读取及控制字符干扰；按权限限制敏感信息。

### 5.3 验证

覆盖 `ls /sys`、`ls -l /sys`、嵌套目录、进入目录再列出、直接读取列出的文件，以及 `/proc`、`/proc/self`、活跃/退出进程目录。验证持续创建退出进程时 ls/ps 仍能结束且结果合理。

## 6. 完善 ps、pkill、killall

### 6.1 ps 选择语义

| 命令 | 选择范围 |
| --- | --- |
| ps | 当前用户、当前控制 TTY 的进程 |
| ps -a | 有控制终端的进程，排除会话首领，不限于当前用户 |
| ps -x | 当前用户的进程，包括无 TTY 的进程 |
| ps -e / ps -A | 系统全部进程，包含服务和其他用户进程 |
| ps -ef | 系统全部进程，完整格式 |
| ps -t pts/0 | 指定控制 TTY 的进程 |

- “当前用户”明确为有效 UID，并在文档与实现中保持一致。
- 支持 `-ef` 和 `-e -f`；`-f` 只影响格式。
- 没有显式选择项才应用默认筛选；显式选择项按文档规定合并，`-e/-A` 选择全部。不能让 `ps -ef` 仍被默认用户或 TTY 条件过滤。
- 统一识别 `pts/0`、`/dev/pts/0`、`tty1`、`/dev/tty1`，不以标准输入输出文件猜测控制终端。
- 当前进程没有控制终端时采用明确行为，不能把所有显示为 `?` 的进程误认成同一个 TTY。
- 默认格式为 `PID TTY TIME CMD`；完整格式包含 `UID PID PPID C STIME TTY TIME CMD`，实现所需的真实元数据，不用固定占位值伪装 CPU 或时间统计。
- 用户名解析失败回退数字 UID；合理排序 PID，定义长命令的显示与转义。
- 进程在读取期间消失时跳过；真正的格式、权限、系统错误按约定报告。

### 6.2 信号工具

- ps/pkill/killall 复用基础工具项目内部的小型 procfs 读取代码，不再依赖 TaskListEntry，不把命令行筛选逻辑塞回 OS 公共库。
- killall 保持完整名称匹配，pkill 保持已承诺的匹配规则与信号参数。
- 批量操作先收集目标快照再发信号，避免循环枚举把刚重启的同名 shell 再次选入。
- 核对 PID 生命周期竞争；若存在复用，使用已有身份或句柄机制避免误操作新进程，不引入没有实际需要的全新公共框架。
- 错误、匹配数量、无匹配和部分权限拒绝的退出码明确且一致。

## 7. 运行时配置与非内置服务加载

### 7.1 路径

服务与会话配置统一平铺在 `/etc/`，不使用 `.conf` 后缀，不使用 `/etc/osinfo/` 子目录：

```text
/etc/services
/etc/sessions
/etc/hostname
/etc/fstab
```

同类运行时配置按 `/etc/<名称>` 规则清点，记录旧配置路径的必要迁移；不要把动态库、链接器、程序、SDK 或镜像当作配置文件搬入 `/etc`。构建侧 `config/` 是开发输入，不能与系统运行时 `/etc` 混为一谈。

### 7.2 单一配置来源

- `./configure` 校验构建配置并生成默认运行时文件，`make install` 统一部署。
- 配置字段至少表达名称、owner、enabled、文件路径与参数、requires、order、ready、timeout、restart。
- 选用简单、可验证且有界的格式；准确规定注释、空白、字符串/参数边界、长度限制及错误定位，不能靠 shell eval 解释。
- 拒绝重复名、未知字段、非法路径、无效引用、依赖环、跨 owner 归属冲突。
- 解析完整配置并验证后再执行相应启动计划，避免半解析半启动。
- 系统安装更新不能直接覆盖用户改过的运行时配置。首次安装创建默认值，升级保留现有配置，并明确默认值变化与迁移策略。
- 本轮只在启动时读取配置；systemctl 的状态修改按受控流程更新内存与磁盘，不引入未要求的热重载。

### 7.3 引导与文件服务

- 文件系统挂载前无法读取磁盘配置，因此只保留建立基础运行环境所需的内置引导信息。
- 将“源码来源 local/external”“加载来源 boot/file”“所属管理者”分开表达，避免项目内源码必然被内置的假设。
- 非内置启动列表不能继续生成 startup.inc 或等价 C++ 数组。
- users/tty/console/guiw 从文件系统加载，退出 GRUB 服务模块列表；不可只改变启动名单读取方式而仍用旧 ProgramId 内置加载。
- GUI 终端和文本 shell 的入口读取 `/etc/sessions`，去掉 sessions.inc 中相应运行时入口常量。
- 不保留配置缺失或文件加载失败时悄悄启动内嵌旧服务的回退。
- 更新 boot 元数据、镜像部署、外部包校验和固定身份检查；保留必要固定角色约束，避免为移除模块而随意破坏 ABI。

### 7.4 受控服务文件加载

- 复用已有 ELF、解释器、运行库和 task.kernel 创建路径；服务镜像当前的链接方式需要核对，不能假定普通动态程序加载路径无需适配即可加载服务。
- 为合法服务启动建立受控授权，验证服务身份、上级、能力上限和可信来源。
- 普通 execute、root 身份、路径名称、请求参数或配置中的任意 role 字段不能自行获得特权。
- 动态普通服务也要有生命周期服务标记；该标记与是否有硬件能力、是否有固定 ServiceRole 分开处理。
- 明确向子服务传递的注册表、控制端点及必要句柄，关闭多余继承，失败时完整回收。

## 8. 父子服务启动、就绪与监护

### 8.1 启动关系

| 上级 | 对象 | 顺序与里程碑 |
| --- | --- | --- |
| init | task | 建立任务服务基础 |
| task | pipe、msgq | pipe → msgq，分别就绪 |
| init | device | task 子服务就绪后激活 |
| device | pci、storage | pci 就绪 → 设备枚举 → storage 就绪 |
| init | fs、mm | storage 就绪 → 根卷挂载 → mm 就绪 |
| init | 文件服务 | 读取配置，默认 users → tty → console → guiw |
| 会话管理者 | 终端、shell | 依赖就绪后按 `/etc/sessions` 建立 |

### 8.2 实现要求

- pci/storage 确实由 device 创建与监护，pipe/msgq 确实由 task 创建与监护，不只是修改日志或配置中的 owner。
- init 不再直接创建或重启这些派生服务。
- 移除当前 pipe/msgq 对 pci 的错误依赖，调整 task/device 的阶段与授权。
- 区分父服务激活、端点可用、自身就绪、子服务组就绪。owner 关系与 requires 关系分别验证，避免把父子就绪错误地建成依赖环。
- 不能仅因端点注册成功就宣布驱动完成初始化或子服务全部可用。
- 每个服务只能有一个监护者；创建句柄、子进程回收、重启和管理请求都归该 owner。
- 使用小型可复用的配置/监护实现，不把多个服务入口重新集中成一个大文件。
- 为启动超时、退出重启、持续失败设置有界行为和退避，防止服务重启风暴。
- 上级退出/重启时明确子服务归属与处理策略，不能留下孤儿服务或重复实例。
- 依赖服务重启后的端点更新和业务状态恢复分别说明；不能把重新注册等同于原来的管道、队列、DMA 或 VMA 状态自动恢复。

## 9. 独立 systemctl 项目与服务保护

### 9.1 基础工具项目布局

```text
osinfo-base-tools/
  coreutils/
  sysinfo/
  mount/
  mkfs/
  systemctl/
  Makefile
```

- **systemctl 是新的独立项目，不是 coreutils 的一个命令目录。**
- 拥有自己的源码、项目配置、调试配置和 build 目录。
- 单独生成 `systemctl/build/packages/systemctl.inpk`，顶层 Makefile 统一构建后汇总 ZIP。
- 更新“四个子项目/四个包”的固定假设，确保复合包、configure、安装和文档包含第五个项目。
- 客户端归 systemctl，OS 负责管理协议和管理端；systemctl 不能直接操作内核私有状态或用 PID kill 替代服务管理。

### 9.2 命令与状态

支持：

```sh
systemctl list
systemctl status [服务名]
systemctl start 服务名
systemctl stop 服务名
systemctl restart 服务名
systemctl enable 服务名
systemctl disable 服务名
```

- 状态包含 owner、期望状态、实际状态、PID、就绪情况、最近退出原因和重启次数。
- start/stop/restart 通过已认证 IPC 路由到实际 owner，按服务身份管理，不能只操作一份过期 PID。
- stop 先记录期望停止，再执行停止，监护器不得立即重新拉起。
- enable/disable 修改持久配置，与是否正在运行区分；对本轮仍不可禁用的基础引导服务明确拒绝或报告限制，不假装成功。
- 被活动服务依赖的对象默认拒绝单独停止，列出依赖；完整停机按依赖逆序处理，不暗中级联停止用户未指定的服务。
- 状态查询与变更分别校验权限；禁止普通进程伪造控制端点或代替其他 owner 管理服务。
- 并发请求串行化，使用服务实例身份/状态检查避免 start/start、stop/restart 产生重复实例或误杀新实例。
- 配置更新使用锁和原子发布；非法配置、写入失败时不破坏原配置，并使内存状态与持久状态的结果可解释。

### 9.3 禁止外部 kill 服务

- 在内核授权层阻止普通终止路径控制服务，不能只在 kill、killall、pkill 前端过滤。
- 即使是 root，普通信号/终止调用也不能直接对服务执行 SIGTERM、SIGKILL、SIGSTOP 等外部生命周期控制；其他会终止、暂停服务的用户发起信号同样核查。
- 覆盖直接 Task API、libc kill、进程组信号和任务句柄终止路径；不能漏掉一个入口。
- signal 0 等存活/权限探测按明确约定处理，不将探测错误实现为停止操作。
- systemctl 由授权 owner 通过受控路径执行优雅停止和必要的超时强制清理，普通程序不能复用该授权。
- 服务身份依据受控启动标记与归属，不按名称匹配；普通同名程序不得被错误保护。
- 服务的正常子应用、TTY shell 不因父进程是服务而自动获得禁止 kill 的标记。
- 服务主动退出、同步异常和崩溃仍然可完成清理与监护处理，不能被生命周期保护阻止。
- 批量信号遇到服务时报告拒绝，继续处理允许的普通目标，正确返回部分失败。

## 10. 修复 `killall sh` 后会话失效

- 每个文本 TTY 建立独立会话记录，保存 shell 任务、控制终端、进程组及期望运行状态。
- shell 正常退出或被 kill 后回收旧任务并按策略建立新会话，恢复可用提示符和输入输出。
- 正确恢复 canonical/echo 等终端模式、前台进程组、控制终端和遗留输入状态。
- 明确会话退出时后代作业、前后台任务及孤儿子进程的处理，不让旧会话进程继续占用前台或泄漏僵尸。
- 会话恢复遵循登录/凭据策略，不因自动重启而获得 root 权限，也不能无意复活已经明确注销的认证状态。
- GUI 标签页区分 shell 退出、读循环 EOF、窗口关闭和主动关标签；只对仍需要的会话恢复，不把主动关闭当故障重新创建。
- 回收旧 PTY、句柄、读线程和映射，重复退出恢复不持续增长资源。
- killall/pkill 使用目标快照，不循环杀新 shell；shell 属于普通会话进程，允许该操作，不能用“禁止 kill 所有受监护进程”掩盖问题。
- 覆盖 tty1–tty6、GUI 多标签页、反复 killall sh、单独 kill、正常 exit、PTY EOF、前后台作业及终端切换。

## 11. 修复鼠标连续点击导致 GUI 崩溃（并且还切换不了其他 tty ）

### 11.1 定位

- 记录触发窗口、控件、标签页数量、点击节奏、按键/滚轮/拖动组合和故障表现。
- 确定是窗口服务、终端应用、输入服务、内核崩溃，还是事件处理死锁；记录 PID、实例变化、退出状态、异常位置和串口证据。
- 检查输入队列与窗口队列的边界、按下/释放配对、合并策略、背压和等待通知；不能错误丢失关键释放事件。
- 检查焦点、命中测试、窗口销毁、断连和标签页切换时的指针寿命、锁顺序及回调竞争。
- 检查缓冲区边界、悬空引用、回复 token、IPC 句柄寿命、栈和堆内存、映射及线程数量。
- 采集必要且有界的诊断信息，避免大量日志改变时序后误判问题消失。

### 11.2 修复与验收

- 根据复现证据修复根因；扩大队列、增加 sleep、忽略错误或自动重启后恢复画面不能单独作为修复。
- 设计覆盖持续快速点击、多轮按下释放、双击、拖动、跨窗口点击、焦点切换、关窗口、新建/关闭标签页的压力场景。
- 超出历史 100 次点击的覆盖，持续时间和轮数依据原故障触发条件确定，并记录实际执行规模。
- 同时验证键盘输入、界面响应、服务实例、事件积压、资源回收和系统存活，防止监护器自动重启掩盖崩溃。
- 用相同或等价操作对比修复前后结果，说明已验证范围与仍存在的限制。

## 13. 实施顺序

按以下顺序推进，只有接口或故障定位证据说明需要时才调整，并记录原因：

1. **基线与清点**：记录既有改动、接口与配置使用方；复现连续点击崩溃、ls /sys 和 killall sh 问题，保存证据。
2. **标准头与 Task API**：按范围迁移，更新符号和调用方，重新构建运行库与依赖项目，建立不混用 ABI 的测试环境。
3. **虚拟目录与进程信息**：先修复 /sys 目录枚举，再实现 procfs 和必要进程元数据，验证文件/目录语义。
4. **进程工具与会话**：迁移并完善 ps/pkill/killall，修复文本 TTY、GUI PTY 的 shell 生命周期及作业控制。
5. **服务启动归属**：实现 task 管 pipe/msgq、device 管 pci/storage，调整权限、就绪阶段和单一监护者。
6. **配置与文件加载**：部署 /etc 下无后缀配置，落实非内置服务文件加载，清除相应编译期表和 GRUB 模块。
7. **服务控制**：建立受控生命周期协议与内核保护，完成独立 systemctl 项目、持久状态及打包。
8. **GUI 根因修复**：利用前面保存的复现与诊断证据完成点击崩溃修复；若与前序模块共享缺陷，先修复共享根因，避免重复工作。
9. **交付集成**：重组详细文档，导出 SDK、重建五个基础工具项目及其他受影响包，更新 packages 和 InfoIDE 所需系统资源。
10. **整体验收**：运行与改动相匹配的构建、权限、故障恢复和真实 QEMU 验证，记录结果与未解决事项。

不要以一项功能完成就宣称本轮全部完成。每阶段记录实际改动、验证命令、结果、剩余问题和当前阻碍；后续从记录继续，不重复执行已通过且没有新变化的验证。
