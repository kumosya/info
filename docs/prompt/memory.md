ring0 纯内核层面和 memory 服务做的事情：页管理，内存映射，共享内存。然后还有页面所有权、引用计数、按页块分配连续物理内存（前面没实现的要实现）。需要实现伙伴算法管理物理页，面向固定类型或固定大小的对象的 Slab / Object Cache，分配大块内存的Buddy Allocator，固定大小 Pool。还有Per-CPU Cache和NUMA-aware Allocator。这些都是写在src/kernel/memory/里的，要分文件夹，一个文件里不要写太多。

以上如果有提供接口，那么除了内存映射，其他的都通过 memory 服务提供接口。

ring3运行的是 MM（Memory Manager） 服务，分为：缺页处理服务（pager），页面回收管理器，共享内存管理器（ring0有对应服务，ring3负责对象化和精细化），虚拟内存区域管理器，页分配策略。

虚拟内存区域管理器需要实现的功能：
- 查找可用的虚拟地址范围。
- 分配、释放和拆分区域。
- 合并相邻且属性兼容的区域。
- 管理匿名映射、文件映射、共享映射。
- 记录映射权限和后备对象。
- 在 mprotect()、munmap() 等操作时更新区域元数据。
- 防止地址范围重叠、整数溢出和非法长度。

用户态页面分配策略（Page Allocator）
P0 · 必须
Ring 0 Buddy 管理物理连续页块；Ring 3 Page Allocator 决定什么时候需要页面、页面用于哪个进程，以及应该选择什么类型的内存对象。
建议支持：
- 匿名内存页面分配。
- 按需分配与延迟提交。
- 零填充页面请求。
- 共享内存对象分配。
- 页面分配失败处理。
- 按进程或服务统计页面使用量。
- 在内存不足时向回收管理器提出请求。
不要在 Ring 3 再实现一个管理真实物理地址的 Buddy Allocator，除非你的架构明确将一部分物理内存作为专用用户态池，并且内核对其授权和所有权有完整保护。

Pager（缺页处理服务）
P1 · 建议在按需分页前设计
Pager 是用户态内存管理体系的重要组成部分，负责决定缺页页面的内容从哪里来。
- 匿名页：提供清零页面。
- 文件映射：从文件系统读取相应偏移的数据。
- 写时复制：请求建立私有页面。
- 被换出的页面：从 Swap Manager 恢复。
- 无效地址：通知内核或调用方发生非法访问，而不是无限重试。
还需要处理并发缺页、重复请求合并、Pager 自身缺页以及 Pager 崩溃后的恢复。

页面回收管理器（Reclaim Manager）
P1 · 按需实现
它负责在内存压力上升时决定回收什么，而不是直接修改页表。
建议逐步支持：
- 按进程统计内存使用量。
- 页面活跃度与近期访问情况的统计。
- 回收可重新从文件读取的干净页面。
- 识别不可回收、固定或正在 I/O 中的页面。
- 协调脏页写回。
- 请求 Ring 0 撤销映射或解除页面固定。
- 内存压力等级和回收失败策略。
先支持明确的页面分类、内存统计和安全回收协议，之后再根据测量结果选择算法。

共享内存管理器（Shared Memory Manager）
建议实现：
- 创建共享内存对象。
- 由授权进程将对象映射到自己的地址空间。
- 支持只读、读写等权限组合。
- 处理共享对象销毁与最后一个映射解除之间的关系。
- 支持 IPC 传递共享内存句柄。
- 可选地支持固定页面和 DMA 缓冲区的不同权限策略。
物理页引用、实际映射权限和最后释放时机仍由 Ring 0 保证；Ring 3 管理器负责协调共享对象的创建、使用和回收策略。
