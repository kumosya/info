## 2. 总体架构与 syscall 边界

目标架构明确为**混合内核**：保留必要的内核机制与可信 Ring 0 服务，其他服务按可行性运行于 Ring 3，通过 Endpoint IPC 协作。

### 2.1 删除 Ring 0 的中断式系统调用

- 删除内核层服务使用的 `int $0x80` 调用路径、分派入口、专用中断门及相关声明、探测、包装与过时文档。
- Ring 0 服务直接调用具有明确职责和类型的内核类方法，不通过 syscall，也不能改成直接调用通用 syscall dispatcher 来伪装完成。
- syscall 只服务 Ring 3；可信服务身份不能由普通 ELF 路径、root 身份、请求参数或普通能力位伪造。
- 处理服务镜像、共享库、符号解析与链接边界，保证 Ring 0 直调确实可用，且 Ring 3 不可借这些符号越权。
- syscall ABI 中不得出现直接端口读写，也不得通过“通用设备命令/操作码”变相保留任意端口操作。
- 必要的端口指令仅存在于可信 Ring 0 硬件实现，通过内核接口调用；面向 Ring 3 的设备服务协议执行授权和参数校验。

### 2.2 syscall 收敛与服务归属

旧编号中的明确保留项：

| 分组 | 旧编号/名称 | 要求 |
|---|---|---|
| Endpoint IPC | 44–47：SendMessage、ReceiveMessage、CallService、ReplyMessage | 保留基础机制并扩展必要语义 |
| 句柄 | 8 GetStandardHandle、16 GetBootstrapHandle、18 CloseHandle | 保留这三个调用入口 |
| 地址空间映射 | 66–68：MapMemory、UnmapMemory、ProtectMemory | 保留必要映射机制 |
| 调度 | Yield、Sleep | 保留直接调用 |
| 必要任务管理 | 经分析必须直接调用的操作 | 最小保留集合，逐项说明原因 |

其余功能改为服务提供：

- 消息队列交给 `msgq` 服务。
- 管道及双向通道交给 `pipe` 服务。
- 设备管理交给 `device` 服务，PCI、storage 等具体职责根据现有对象模型合理分工。
- 内存管理策略和共享内存等服务功能交给 `memory` 服务；底层页表、页框、隔离、权限校验等机制留在内核。
- 进程管理优先交给 `task` 服务；对必须读取/修改调用线程上下文，或迁移造成明显效率、耦合、引导问题的操作，允许有依据地保留直接内核调用。
- 未明确要求迁移到 Ring 3 的其余服务默认放在 Ring 0，不把“服务化”自动理解成“全部用户态化”；保留或调整现有 Ring 3 服务必须说明依据。
- `msgq` 和 `pipe` 优先评估 Ring 3 实现。只有在不新增 syscall 且保持所需语义的条件下可行才迁移，否则保留为 Ring 0 服务对象并说明具体阻碍。
- 服务化必须改变实际调用路径、状态所有权和资源清理方式，不能只给原 syscall 包一层类或套一层 IPC 后原样保留全部入口。

对旧 `CreateEndpoint`（43）单独说明引导及工厂方案：Endpoint 创建是必要能力，但不能遗漏，也不能以此擅自增加 syscall。可评估现有保留入口的明确子操作或可信服务工厂协议；必须证明无循环启动依赖且授权正确。

对每个旧 syscall 列出：旧编号、旧名称、目标服务、执行级别、新调用路径、是否删除、保留原因。最终 ABI 只能包含上述基础入口和确有必要的任务机制。

### 2.3 编号顺序与 ABI 一致性

最终 syscall 连续排序，顺序为：

1. Endpoint IPC。
2. 上述三个句柄调用。
3. 三个内存映射调用。
4. 剩余必须直接调用的任务/线程/同步机制，包含 Yield、Sleep。

统一更新枚举、宏、分发表、参数布局、汇编探针、libc/POSIX 适配、所有服务和应用及文档。检查旧硬编码编号、数组长度、Count 边界与非法编号处理。允许随全量重构调整 ABI，不保留无需求的双 ABI 或旧分派路径。

**禁止为了本任务额外增加 syscall 编号。** DuplicateHandle、TransferHandle、RestrictHandleRights、取消、服务发现、TerminalId 等是能力需求，不代表同名 syscall。先设计如何通过现有句柄入口的受控操作、既有 IPC 消息/参数或服务协议实现，给出清晰的 ABI 契约；不能借复用入口绕过权限检查。

### 2.4 current 与代理调用身份

- 全面检查依赖 `task::getCurrent()`、`Thread::getCurrent()`、当前地址空间、凭据、信号掩码、父子关系和句柄表的路径。
- IPC 后 `current` 是服务线程，不能继续把它当成原调用者。使用内核认证的发送者身份及受限请求上下文；PID 字段本身不是授权凭证。
- 对调用者资源的操作明确传入目标 Task、地址空间、对象引用与授权上下文；禁止临时修改 CPU current 来冒充客户。
- fork、exec、线程创建/退出、信号返回等需要原始执行上下文的路径逐项审查，必要时留在直接任务管理调用中。
- 接收、回复及异步处理期间持有必要的身份/对象引用，防止调用者退出及 PID 重用引发悬空访问或授权混淆。

## 3. 服务与 OS 库对象化

- 每个服务由一个或几个职责清晰的对象组成，实际持有状态并负责初始化、请求分派、工作循环和清理。
- 检查全部服务程序，包括内部辅助函数、匿名命名空间函数、线程回调和跨文件函数；业务实现不得残留独立自由函数。
- 线程入口和工具逻辑使用所属类的成员或静态成员，避免只把全局函数搬进一个巨型静态类。
- `main`、`userMain`、`_start` 等工具链必需入口，以及确有外部 ABI 限制的桥接符号，仅允许最薄转发；逐项记录不可改为成员的原因，业务逻辑放在对象中。
- `include/os-c++/os/terminal.h` 改为 `os::Terminal` 类，终端读写、切换、前台进程设置及 TerminalId 管理归入该类。
- 删除旧 TerminalId syscall；沿启动参数、运行时状态、继承和 exec 路径保持终端身份一致，不新增 syscall。
- OS 库内除最终保留的底层 syscall 包装外，所有功能均使用类方法，覆盖运行时、服务发现、task、file、pty、input、内存、设备及相关 GUI 库接口和内部辅助实现。
- 公开接口、实现和调用方一起更新，不遗留旧自由函数兼容壳。标准 C/POSIX ABI 可保留必要的适配入口，其 OS 侧实现调用对象接口。
- 对拥有句柄等资源的对象明确所有权；采用适合 freestanding 环境的 RAII、不可复制/可移动规则，不引入无必要的通用框架。

## 5. 核查并修复 P0–P4

以下来自外部代码审查，均为**待核实的假设**。对每项报告“存在/部分存在/不存在”、具体文件和符号、触发条件、已有保护机制、修复及验证证据；不得直接把推测写成已证实漏洞。

### P0：句柄传递的原子性与实际接收者

检查 `transferHandles()`、`enqueueMessage()` 和接收/回复路径：

- 是否逐个安装句柄，中途失败不回滚；是否先传句柄再验证发送权限、队列容量。
- 是否错误地把 Endpoint owner 当成最终领取消息的线程所属 Task。
- 采用明确的事务边界：先校验权限、所有输入句柄和资源条件，暂存对象引用及衰减后的权限，再向最终合法接收者提交句柄安装。
- 队列中的消息可持有待交付的对象引用，避免过早在错误 Task 安装句柄。Endpoint 的合法接收者规则必须明确并被执行。
- 接收方句柄表扩容失败、用户缓冲区拷贝失败、超时、取消、队列销毁及回复失败均应回滚未提交资源，释放暂存引用/授权。
- 明确 copy 与 move 的提交点：失败不遗留接收句柄、扩大 ACL 或意外丢失发送方句柄；成功后关闭/保留源句柄符合约定。
- 跨句柄表并发操作需要固定锁顺序或等价安全协议，不能为原子性引入死锁。

### P1：显式 RPC 请求关联

- 核实 `Endpoint::reply()` 是否只以当前服务线程寻找请求。
- 引入内核管理的唯一 Request ID 或不透明 Reply Token，绑定原始 Endpoint、调用者、请求状态及获授权的回复者。
- 服务端通过接收结果取得 token，并在回复时显式提供；明确多线程服务间能否移交 token 及相应授权。
- 拒绝伪造、错误 Endpoint、错误服务身份、重复回复，以及取消/超时/销毁后的迟到回复；处理代际和 ID 重用。
- 支持同线程持有多个请求及不同回复顺序，取消隐含的“每线程只能有一个待回复请求”约束。

### P2：阻塞、销毁和通知语义

- 核实固定 8 槽队列、满队列发送等待、空队列接收等待的实现。
- 定义 Endpoint 关闭/销毁、服务退出、信号、线程/进程终止、取消、超时各自的返回结果及清理责任。
- 等待节点只能完成和摘除一次。检查 `prepareWait()`、等待队列入队、释放锁、实际阻塞以及唤醒间的全部竞态，避免丢失唤醒、重复唤醒和栈上等待节点悬空。
- 明确等待者顺序与公平性，防止无限饥饿；不必承诺无法实现的严格 FIFO。
- 明确 IRQ 通知与普通消息的优先级、合并、溢出和丢弃策略；中断上下文不得阻塞或执行不安全分配。

### P3：Task、Thread、地址空间和内核对象生命周期

- 核实 `Task::create/destroy`、失败路径、`waitForChild()`、GetTaskState、HandleTable 的 `entries_`、线程栈及地址空间是否最终回收。
- 检查全局任务表、父子链、调度/等待队列、句柄表、IPC 请求和设备通知持有的引用。
- 区分退出、保留退出状态、父进程回收、最后引用释放；不可在 Terminated 时直接释放仍可被 waitpid/GetTaskState 访问的 Task。
- 定义僵尸、孤儿、已回收状态和多观察者查询语义，防止重复回收和悬空句柄。
- 建立明确的对象引用、借用及最终销毁规则，覆盖所有句柄类型和异步请求；结合现有内存分配方式选择最小实现。

### P4：SMP exec/退出的地址空间安全回收

- 跟踪 `Task::commitExec()`、其他线程终止、调度切换、CR3、TLB shootdown、远端 IPI 和页表/物理页释放。
- 发送重新调度 IPI 不等于远端 CPU 已停止使用旧地址空间。
- 建立明确协议：阻止新使用者进入，要求活跃 CPU 停止使用旧根并确认，完成必要 TLB 同步，最后回收旧页表和页面。可采用确认屏障或适合现有调度器的延迟回收。
- 不得持有远端 CPU 完成确认所需的锁等待确认；明确本地线程的切换时机和不会返回旧用户态的条件。
- exec 失败保持原地址空间可用，成功提交及退出回收必须覆盖远端线程并发创建/调度/结束等竞态。

## 6. 新增 IPC 超时、取消与请求标识

在现有 SendMessage、ReceiveMessage、CallService 与 ReplyMessage ABI 基础上扩展，不新增 syscall：

- 统一使用单调时钟截止时间，明确单位、精度、溢出、无限等待与立即返回编码。
- CallService 的截止时间覆盖入队等待和等待回复的总过程，不在重试时重置超时。
- 定义 SendMessage 成功意味着“已入队”还是“已交付”，及取消、句柄 move 与该提交点的关系。
- 支持取消阻塞等待和仍未被服务端领取的请求。已被领取的请求明确采用协作取消还是仅结束调用者等待，不能声称自动撤销已有服务副作用。
- 提供无新 syscall 的跨线程取消入口及授权规则；不能仅依赖被阻塞线程自己发起取消。
- 定义 RPC 状态机及完成的唯一胜出规则，覆盖排队、领取、回复、超时、取消、服务死亡及 Endpoint 销毁。
- 使用明确且一致的错误类别区分 WouldBlock、Timeout、Interrupted/Cancelled、端点关闭、对端死亡；错误码与 POSIX 映射同步更新。
- 超时或取消后的迟到回复安全失败，所有请求、等待节点、对象引用及未交付句柄被正确清理。
- 不用高频 sleep 轮询代替内核正确的阻塞/定时器/唤醒机制。

## 7. 句柄复制、转移、权限及引用

- DuplicateHandle：当前进程内复制句柄，可指定不超过源句柄的权限。
- TransferHandle：通过 IPC 传递，明确 copy 与 move 两种语义；成功、失败、取消的源句柄处理与 P0 事务规则一致。
- RestrictHandleRights：只能缩减权限，拒绝提升或未知权限位；明确仅作用于该句柄还是其他已复制句柄，不能隐含承诺全局撤权。
- 对内核真正消费的 rights 做类型相关检查，不能只修改表中数值。
- 支持不可继承标记，以及执行新映像时关闭（close-on-exec）标记；分别说明 fork、spawn、exec 的继承规则。
- “关闭时执行”同时落实为可靠的关闭释放规则：close/closeAll 调用对象相应的引用释放和必要清理，不能执行用户提供的任意内核回调。若项目已有其他具体定义，先核实再保持一致。
- 所有句柄类型具有一致的 retain/release 规则；最后引用与逻辑关闭的区别明确，Endpoint 关闭可以唤醒等待者，而对象物理释放等待引用归零。
- 标准句柄、bootstrap 句柄、服务缓存、设备资源及共享内存映射均纳入所有权检查。

## 8. 统一服务管理与故障恢复

- 基于现有 init 注册表设计独立的服务管理对象/服务，优先 Ring 3，不新增 syscall，避免重新造一套不兼容的服务发现机制。
- 支持服务名称注册、查询、注销/失效和服务代际，明确名称长度、容量及错误处理。
- 名称注册、替换、发布句柄及查询均验证内核认证身份；受保护服务名称不能被普通进程抢注或覆盖。
- 发布的 Endpoint 句柄仅带客户端所需权限，不泄露接收、管理或任意设备操作权限。
- 使用现有任务机制、Endpoint 生命周期或受控协议实现服务死亡检测，释放注册表引用并标记失效；不得为死亡通知新增 syscall。
- 服务重启后可安全重新注册；陈旧 Endpoint/token 明确失败，客户端丢弃缓存后可重新发现新一代服务。
- 自动重连不能默默重放已产生副作用的非幂等请求；区分传输失败、执行结果未知和可重试请求。
- 明确由 init 或服务管理对象承担的重启策略与权限，不要求为本任务引入无需求的复杂监督框架。
- 证明 bootstrap、服务管理、memory、task、pipe/msgq 与其他核心服务之间不存在循环依赖；给出启动、失败和重启顺序。

## 10. 实施次序与验证

按依赖组织可验证阶段：事实核查及 ABI/身份设计 → 生命周期和句柄事务基础 → IPC token/超时/取消 → Ring 0 直调与 syscall 收敛 → 服务迁移/对象化/独立构建 → 服务恢复和文档校验。可按实际耦合调整顺序，保持各阶段最终可集成。

至少验证以下真实行为，优先复用现有测试、自检和 QEMU 流程，不为简单改名编写镜像实现的测试：

- P0：无权限、队列满、第二/后续句柄无效、接收表分配失败、用户拷贝失败时无泄漏和授权副作用；不同合法接收者场景符合约定。
- P1：多个未完成 RPC、乱序回复、嵌套调用、错误 token、错误回复者、重复及迟到回复。
- P2：队列满/空、超时边界、跨线程取消、信号中断、Endpoint 关闭、服务死亡及唤醒/阻塞竞态；IRQ 与普通消息并存。
- P3：重复创建/退出/wait、fork/exec、初始化失败、孤儿进程、持有退出 Task 句柄等情况下资源最终回到稳定水平；不释放仍被使用的对象。
- P4：多 vCPU 下同进程线程运行时反复 exec/终止，确认远端切换和 TLB 同步完成后才释放旧页表；单核也需正常运行。
- 权限：复制降权、拒绝提权、不可继承、close-on-exec、copy/move 成功和失败、代际失效和最后引用回收。
- 服务：安全注册、抢注/替换拒绝、死亡失效、重启注册、客户端缓存失效和重新连接、不重复执行非幂等请求。
- 回归：启动、fs/storage/device/input、tty/PTY、shell、管道、消息队列、共享内存、GUI 终端和窗口服务。
- 构建：根目标、`make -C user`、共享库/服务/应用链接、软件包、镜像和增量依赖。先检查实际工具链与目标，不凭空宣称构建通过。
- 静态审计：无服务用 `int $0x80`、无 Ring 0 调 dispatcher 的替代路径、无端口 syscall/代理操作码、无旧编号引用、无业务自由函数残留、无过时文档链接。

使用现有 `make check` 等目标前先阅读其实现；说明测试覆盖范围，不能用编译或静态搜索代替运行时并发验证。工具链/模拟器不可用时，明确记录阻碍、已完成验证和可复现命令，不伪造结果。
