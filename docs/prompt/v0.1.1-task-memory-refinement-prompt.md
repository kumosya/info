## 2. 已核实的现状与必读入口

以下仅是编写本 Prompt 时的事实，执行前再次核对：

- Ring3 MM 位于 `user/mm/`，pipe/msgq 位于 `user/pipe/`、`user/msgq/`。
- Ring3 PCI/storage 位于 `src/pci/`、`src/storage/`，尚未归入 device 子树。
- `src/kernel/task/core_service.cc` 聚合了 PCI、device、system、task 等驻留服务实现；PCI 没有独立的服务目录。
- `src/kernel/memory/service/service.cc` 包含 `Map`、`MapPages`、`MapSharedTarget`、`UnmapTarget`、`ProtectTarget` 等分发，需要逐项核对与 syscall 的重叠。
- `include/os-c++/os/core_service.h` 声明对应服务协议；`include/os-c++/os/abi.h` 同时公开 syscall 包装和服务客户端。
- `include/os-c++/os/service.h` 有读取 CS 的内联检查；`lib/os/runtime.cc`、`lib/os/service_start.S` 也有 CS 相关实现，需要区分公共运行库职责与服务专属启动检查。
- `src/fs/sysfs.cc` 将 `/sys/kernel/ostype`、`osrelease`、`hostname` 的内容写死；其中版本为 `0.1`、hostname 为 `localhost`。仓库已有 `script/etc/hostname`。
- `packages/ld-osinfo.inpk` 及 `packages/ld-osinfo/` 存在，Makefile 中动态链接器被纳入包产物链路。
- sysinfo、mount、mkfs、coreutils 仍位于 `user/`，各自存在包配置或产物。
- InfoIDE 当前为 Python 实现，文档仍介绍 Windows/WSL 和浏览器界面。

重点阅读根 Makefile、`user/Makefile`、`src/init/`、服务注册与权限检查、`src/kernel/task/syscall/`、内存服务与底层映射实现、`user/mm/`、`lib/os/`、SDK 导出脚本、镜像安装脚本及外部包清单。跨项目修改前，读取对应项目的说明、配置和构建入口。

## 3. 目录与服务边界

### 3.1 基本规则

- Ring3 系统服务属于 `src/`，不能因运行在用户态而放进 `user/`。
- Ring0 服务与机制属于 `src/kernel/`。Ring3 服务与 Ring0 驻留端点分别实现，不能只改名字而继续混放。
- `user/` 用于应用程序。不要误将 `src/kernel/user/` 中的 ELF 加载等内核机制按名称迁成普通应用。
- 每个服务拥有独立目录和实现文件；聚合注册文件只做注册、发现或薄分发，不堆放多个服务类及业务实现。
- `.kernel` 表示 Ring0 驻留服务端点，不要求把它变成可加载模块、独立进程或单独 ELF。

### 3.2 明确的迁移落点

| 现有位置或实现 | 目标位置 | 要求 |
| --- | --- | --- |
| `user/mm/` | `src/mm/` | Ring3 内存策略服务 |
| `user/pipe/` | `src/task/pipe/` | 独立 Ring3 pipe 服务 |
| `user/msgq/` | `src/task/msgq/` | 独立 Ring3 msgq 服务 |
| `src/task/main.cc` 中 task 服务 | `src/task/` | 保留独立入口，与 pipe/msgq 分开构建 |
| `src/pci/` | `src/device/pci/` | Ring3 PCI 服务 |
| `src/storage/` | `src/device/storage/` | Ring3 存储驱动服务 |
| 聚合文件中的 `pci.kernel` | `src/kernel/device/pci/` | 独立服务文件与目录 |
| 聚合文件中的 `device.kernel` | `src/kernel/device/service/` | 与 PCI 服务分别实现 |
| 聚合文件中的 `task.kernel` | `src/kernel/task/service/` | 不与调度、线程、syscall 实现混为同一服务文件 |
| `memory.kernel` | `src/kernel/memory/service/` | 保留真实内存机制服务，移除重复 syscall 入口 |

其他 Ring0 服务也按其所属子系统创建独立服务目录，先列清单再确定路径。没有实际实现的服务不要创建空目录或占位服务。storage 的现有 Ring0 专属代码若存在，归入 `src/kernel/device/storage/`；不得为目录对称而凭空新增 storage.kernel。

同步更新头文件引用、源文件发现规则、链接目标、boot 模块、服务角色、启动顺序、依赖与审计脚本。避免递归源文件扫描把多个服务入口链接到同一个 ELF。

## 4. syscall、任务与内存边界

核心要求：**syscall 已实现的能力，不得在 Ring0 服务协议中再次提供等价入口；map 不做成 memory.kernel 的重复服务。**

先建立操作对照表：操作名称、现有 syscall、Ring0 服务操作、调用方、权限要求、迁移后的唯一入口。至少覆盖 map/unmap/protect、共享映射、页对象映射、目标进程操作，以及 task.kernel 中可能重复的任务操作。

实施要求：

1. 根据真实调用链识别重复能力，不能只按枚举名称判断，也不能通过换名保留等价 RPC。
2. 已由 syscall 承担的映射操作，客户端回到该 syscall 路径；移除重复服务分发、客户端包装、枚举引用和遗留调用。
3. 页表修改、物理页管理、TLB shootdown、地址校验、权限校验及回收同步仍是内核机制。去除服务入口不等于删除机制本身。
4. Ring3 MM 负责 VMA、匿名与文件映射策略、缺页策略、COW 元数据、共享对象策略和回收策略，不将这些策略重新塞入 Ring0。
5. 对跨进程映射、pager、COW、共享页等需求，明确现有 syscall 能否表达。不能为了清理服务而增加任意 PID 映射、物理地址暴露或权限绕过；也不能以“MM 需要”为由直接保留重复服务。确有接口缺口时，给出具体缺口、最小方案与权限模型，再按适用确认规则处理。
6. 区分请求入口和内部机制复用。syscall 与必要内核组件可复用同一受检机制实现，但不能维护两套映射算法或授权逻辑。
7. 协议变更同步重建所有相关组件，避免枚举编号变化导致旧客户端误调用。存在真实兼容要求时明确处理，不增加无需求的长期兼容层。
8. 保持任务退出、exec、fork、线程清理、句柄引用、Endpoint 取消、MM 元数据失效和地址空间 generation 之间的一致性。
9. 不擅自扩展调度算法、NUMA 策略、swap、MAP_FIXED 或其他未要求功能；现有不支持能力继续明确返回错误。

## 5. 公共 os/ 头文件清理

- 审计 `include/os-c++/os/` 及 SDK 实际导出的其他 os/ 头文件。
- 公共头文件不得包含 CS 读取、Ring 检查、原始端口 I/O、控制寄存器或其他服务专属硬件操作实现。
- 将服务专属检查移回相应服务或私有服务启动实现。确有多个服务共同使用时，只在非 SDK 的内部层复用，不能再次公开到应用头文件。
- 端口及特权硬件操作归属对应 Ring0 设备实现，不能搬入 Ring3 服务直接执行。
- 公共头文件保留合理的 ABI 数据结构、协议声明、客户端接口；文件 I/O 接口不属于本次禁止的硬件 I/O。
- 检查 `lib/os/runtime.cc` 与 `lib/os/service_start.S`，解释 CS 检查的实际用途并处理服务专属逻辑，不能只删除头文件中的一段代码便宣称完成。
- 保留必要的 syscall 汇编入口，不将“禁止 CS/硬件 I/O”扩大解释为“禁止所有汇编”。

## 6. 系统版本与 hostname 配置

目标：系统版本有唯一配置来源，VFS 读取配置；hostname 使用实际配置，不能继续写死。

优先采用简单文本文件，例如 `/lib/version.1`。用户允许配置文件或真正的共享库，但没有可执行 ABI 需求时不要引入 version.so；文本文件不得伪装成 ELF `.so`。实施前确定最终路径与最小格式，并在代码和文档中统一。

- 本次系统版本为 `0.1.1`。先区分系统版本、内核 ABI 版本、SDK 版本和独立软件包版本，不全仓库盲目替换 `0.1`。
- hostname 优先复用 `/etc/hostname` 及已有镜像配置源，不另造相同用途的配置。
- `/sys/kernel/osrelease`、`/sys/kernel/hostname` 和 sysinfo 等消费者展示一致的配置结果。
- 配置读取在 FS 内部使用底层文件访问路径，不能从 FS 服务内通过公共客户端向自己发 RPC，或读取同一合成节点造成递归和死锁。
- 明确配置加载时机、缓存及生效方式；首期可在根文件系统就绪时加载，不为此引入文件监听或配置服务。
- 元数据读取不应无条件依赖实时 CPU/内存统计请求成功。uptime、CPU 数和内存统计继续来自实时机制接口。
- 对缺失、空文件、非法内容、超长内容、换行、偏移读取和截断读取规定有界行为。必要回退可保留，但正常路径必须实际读取配置，不可静默掩盖部署失败。
- 构建和镜像流程安装配置文件，确保全新构建不依赖工作区残留文件。

## 7. ld-osinfo 与系统镜像绑定

- ld-osinfo 属于与内核及加载 ABI 配套的系统运行组件，不作为普通 `.inpk` 应用包发布或安装。
- 保持现有应用需要的解释器路径 `/lib/ld-osinfo-x86-64.so`，除非确认存在必须改变的技术原因；不因移出包系统而无故改变 PT_INTERP。
- 由 OS 构建直接生成并由基础镜像安装流程部署动态链接器。
- 清理其 `.inpk` 生成、导入、包清单及包管理路径，避免旧包产物继续被镜像拾取。删除具体文件前遵守确认机制。
- SDK 可包含应用链接所需信息及必要配套文件，但不把 ld-osinfo 当作可独立替换的普通包依赖。
- 普通应用包不能覆盖受系统管理的动态链接器路径；核对现有安装器的冲突与保留路径规则，做最小必要适配。
- 验证内核加载器、动态链接器、共享库、SDK 与镜像的一致性，以及缺失解释器时的明确错误行为。

## 8. 拆分 osinfo-base-tools

将 sysinfo、mount（包含 umount）、mkfs、coreutils 迁入 `D:/osinfo/osinfo-base-tools`，形成独立构建项目。

- 先清点所有命令、共享头文件、数据文件、包配置、权限要求与构建依赖，尤其保留登录、用户管理、shell、信号等现有行为。
- 独立项目仅依赖导出的 SDK 和工具链，不直接引用内核私有头文件或通过相对路径偷用 OS 仓库源码。
- 参考现有 guiw/inpkg 外部项目集成方式：独立构建，产物经明确导入后由 OS 镜像安装；OS 主构建不隐式进入相邻源码目录编译。
- `osinfo-base-tools` 首先是独立项目边界；是否合为一个包依据现有包格式和升级边界决定，不能把项目拆分误解为必须强行合包。
- 保持命令安装位置、必要权限和共享文件一致，避免新旧包重复占用安装路径。
- 同步 SDK 使用方式、外部包清单、导入与安装流程；缺少必需包时给出可操作的错误，不静默使用旧缓存。
- 原仓库不保留两份生效源码或两套基础工具构建规则。旧源码与产物清理按确认后的迁移清单执行。
- 不顺带重写这些命令，也不改变普通应用仍可放在 `user/` 的规则。

## 9. InfoIDE 首期：Linux C++ CLI

在 `D:/osinfo/infoide` 中实现 Linux 原生 C++ 命令行工具 `osinfo`。当前不做 GUI，不维护 Windows 启动、浏览器服务或 WSL 桥接。

最小工作流：

```sh
osinfo create hello
cd hello
osinfo build
osinfo pkg
```

### 9.1 项目配置

优先沿用并明确现有 `osinfo-project.json`，避免无必要另造格式。至少支持：

- 项目名称、版本、源文件与目标类型。
- SDK 位置、编译器选择；涉及 C 和 C++ 时分别定义对应工具。
- 头文件搜索目录、库目录、链接库选择，以及必要编译和链接参数。
- 安装映射和 `.inpk` 打包元数据。
- 已有共享库目标、库依赖及 runpath 的实际使用场景，避免破坏 guiw/inpkg 等现有项目。

规定相对路径以项目配置所在目录为基准。配置优先级要简单、可解释，错误应指出具体字段。不要在没有使用场景时设计插件体系或通用构建语言。

### 9.2 命令行为

- `create` 生成最小可构建示例与配置；目标目录已存在且有内容时明确失败，不能覆盖用户文件。
- `build` 读取配置，编译并链接至项目自己的构建目录；选择的库确实进入链接结果，编译器和包含目录配置真正生效。
- `pkg` 生成兼容现有安装器的 `.inpk`，检查产物完整性及安装映射；明确是否自动调用 build，不打包过期或失败构建的产物。
- 提供基本帮助、清晰退出码和子进程错误信息。
- 使用结构化参数启动编译器与打包所需子进程，不拼接 shell 命令；正确处理路径空格和参数边界。
- 不把用户配置中的字符串作为 shell 脚本执行，临时文件和失败产物不能伪装为成功结果。

核心项目生成、配置读取、编译调度和打包使用 C++。不能只写一个 C++ 外壳再调用现有 Python 实现完成核心工作。允许继续调用系统编译器、链接器等合理工具；是否复用系统归档工具由现有包格式决定，保持兼容即可。

先识别现有 Python 功能与新 CLI 的对应关系，再给出具体替代和旧入口退出清单。不要把与本次无关的镜像脚本、全部测试脚本一并重写。

## 12. 验收标准

### 12.1 静态与构建

- `user/` 不再承载 Ring3 系统服务；MM、pipe、msgq、PCI、storage 路径符合目标表。
- Ring0 各服务有独立目录与实现，聚合文件没有遗留完整服务类；没有为凑目录新增虚假服务。
- 公共 os/ 头文件不含 CS/硬件 I/O 实现，SDK 不泄露内核私有实现。
- syscall 与服务能力对照表中的重复入口已清理，相关协议、客户端、调用方和文档保持一致。
